# CINS Rules

The `cins` app is a multi-pass LLM extraction pipeline for insurance commission documents (CINs/CICSs). It is the most complex app in the backend — understand the pipeline flow before making changes.

## Pipeline Overview

Extraction runs in sequential passes defined in `schema/extraction_passes.py`:

1. **Pass 0** — document cleaning & table detection (email, master data, table structure)
2. **Pass 1** — metadata extraction
3. **Pass 2** — master data + products extraction (LLM or codegen)
4. **Pass 3** — rules extraction (LLM or codegen)
5. **Validation** — schema validation + rule overlap checks

Entry point: `processors/core/pipeline.py`

## Structure

| Path                       | Purpose                                                                                                                                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `processors/core/`         | Pipeline orchestration (`pipeline.py`), LLM extraction (`llm_extract.py`), codegen executor (`code_gen_executor.py`), raw→CICS transformer, sheet-visibility predicates (`sheet_visibility.py`) |
| `processors/extractors/`   | File-type handlers: PDF, EML, Excel→CSV, sheet classifier                                                                                                                                       |
| `processors/content/`      | Content utilities: cleaning, CSV→Markdown, indexer, prompt preparation                                                                                                                          |
| `processors/llm_services/` | LLM client wrappers                                                                                                                                                                             |
| `prompts/`                 | Markdown prompt templates — one file per pass                                                                                                                                                   |
| `schema/`                  | CICS data model (`cics_model.py`), JSON schema, extraction pass definitions, raw extraction model                                                                                               |
| `validators/`              | Schema validator, rule overlap checker, raw extraction validator, row/coverage integrity, state column alignment, state+RTO presence, Chola product hierarchy, Chola make/model (MMV)           |

## Rules

- **Never skip passes** — each pass feeds the next; skipping corrupts downstream results
- **Prompts are versioned by filename** — do not rename prompt files without updating all references in `content/prepare_prompt.py` and `schema/extraction_passes.py`
- **Schema changes require migration**: updating `cics_model.py` or `commission_schema_v1.json` must be reflected in both the Pydantic models and the JSON schema file simultaneously
- **Codegen path vs LLM path** — passes 2 and 3 can run as LLM extraction or codegen; the executor in `code_gen_executor.py` sandboxes generated code — do not relax sandbox restrictions
- **Raw extraction model** (`schema/raw_extraction.py`) is an intermediate representation — do not persist it directly; always transform via `raw_to_cics_transformer.py`
- **Validators are non-optional** — always run `validators/validate.py` after transformation; never return unvalidated CICS output to callers
- **LLM calls are expensive** — add new passes only if strictly necessary; prefer extending an existing pass prompt over adding a new pass
- **Prompt templates use Jinja2** — keep logic minimal in templates; heavy pre-processing belongs in `content/prepare_prompt.py`
- **Sheet classification** (`extractors/sheet_classifier.py`) determines which sheets feed which passes — changes here affect the entire pipeline
- **Hidden worksheets never feed extraction** — Excel tabs whose `sheet_state` is `hidden` / `veryHidden` are scratch pads and stale grids. They are still indexed and classified (the UI has to show what was skipped, and a hidden sheet classified `commission_data` is the signal that the wrong tab was hidden), but they never produce rules and never enter a Pass 1/2/3 prompt. Every consumer must derive its sheet sets from `processors/core/sheet_visibility.py` (`derive_sheet_sets`, `is_sheet_visible`, `hidden_sheet_names`, `visible_sheet_names`) — **never inline the visibility comparison**. The moment two call sites compute it differently, the pipeline routes a different sheet set than the one it pre-created `PENDING` `ExtractionPass` rows for, and the UI shows passes that never complete. The filter fails open: a classification entry with no `visibility` key (anything indexed before `INDEXER_VERSION` 1.4, plus `image::` pseudo-sheets) reads as visible. `CINS_SKIP_HIDDEN_SHEETS=false` restores pre-change behaviour without a redeploy, and must keep lifting _every_ gate, including the `rerun-pass` API rejection — not just the routing filter. Contract is pinned by `cins/tests/test_hidden_sheets.py` and `commission_intake/tests/test_hidden_sheet_api.py`
- **Pass 0C table boundaries are not safe to trust verbatim** — the prompt's "Shared Header Rule" makes the LLM emit cumulative `end_row` values for stacked sub-tables under one shared column-header block (one Two-Wheeler grid produced 24,006 rules instead of ~3,000 before the fix). `detect_csv_tables` post-processes raw LLM boundaries through `_dedupe_overlapping_table_ranges`, which (a) reshapes cumulative siblings — same `(start_row, col band)`, monotonic `end_row` — to "shared header band + own data band" using `header_row_count` from `metadata.formatting.detected_header_rows`, and (b) clips classic overlaps where a later commission table's `start_row` falls inside the prior table's range. Only `table_type == 'commission'` is reshaped; `master` and `notes` are left intact. See `cins/tests/test_table_dedupe.py` for the contract.

- **A merged header labels its visible cells even when its top-left is hidden** — `excel_to_csv.expand_merged_cells` propagates a merged value to every VISIBLE cell of the range, not only ranges whose top-left cell is itself visible. Chola's `TW july` hides columns AX and BB, which are exactly the top-left cells of `AX4:AZ4 -> "Hero vs Bajaj"` and `BB4:BE4 -> "Bajaj"`; the old top-left guard dropped those makes from the visible sibling columns, so their rules carried no `vehicle_make` and two different SCOOTER columns collapsed onto byte-identical conditions with different payouts. A fully hidden range still contributes nothing — there is no visible cell to write to — so hidden scratch content cannot leak in. Contract in `cins/tests/test_merged_header_expansion.py`. Changing the indexed CSV shape means bumping `INDEXER_VERSION` (this was 1.6).
- **Side-by-side grids must be split on the column band** — a sheet can hold two independent grids in the SAME rows. Chola's Two-Wheeler sheet is 57 columns wide: columns 2-41 are one grid and 42-56 another, each with its own `State`/`Type` key columns and 125 data rows carrying both. Pass 0C reports it as ONE table, so the second grid's rows are attributed the first grid's state (`KL/LD` vs `KL` on the same row) and its make-group headers — which sit in blank label cells — read as continuations of the first. `detect_csv_tables` runs `_split_side_by_side_tables` after `_dedupe_overlapping_table_ranges` (row ranges settled first, so each block inherits corrected `data_ranges`). Detection is deliberately narrow: `table_type == 'commission'` only, the header row must repeat its **leading key signature** (the first two adjacent non-empty labels, compared on first word only — the real sheet spells the same column `State (RTO)` in one block and `State` in the other), and blocks must be separated by more than one column so a legitimately doubled label pair never triggers it. Only `start_col`/`end_col` are set; row ranges are never touched. Contract in `test_table_dedupe.py::SideBySideTableSplitTests`.

- **NCB is a numeric percentage band, and the boolean beside it is not vestigial** — `RuleConditions` carries `ncb_start_range`/`ncb_end_range` (0-100 inclusive) parsed from the grid's verbatim label by `_parse_ncb_range`, plus the legacy `ncb` boolean **derived** from that band. Four invariants, each of which has already bitten:

  - **Absent NCB is `(None, None)`, never the open `(0, 100)`** used by gvw/cc/seating. `rule_overlap_checker._is_range_constrained`/`_constrained_dims` and `_has_conditions` all key off null-ness, so an open sentinel makes `ncb` a constrained dimension on _every_ rule of _every_ document and shifts the `set(overlapping_dims) == all_dims` complete-overlap verdict globally.
  - **`ncb_start_range`/`ncb_end_range` belong in `_DEDUPE_SCALAR_FIELDS`, NOT `_DEDUPE_RANGES`.** They must join the de-overlap **group key** (or a three-tier ladder — bands `25-45` and `45+`, both `ncb=True` — shares one key and the CC boundary walk fuses two distinct tiers' ladders), but must never enter the walk itself, which would rewrite bands parsed verbatim from the grid. A two-tier ladder is separated by the boolean alone, which is why the boolean stays.
  - **The band and the boolean share the dimension label `"ncb"`** in `_RANGE_KEY_TO_LABEL`. `_constrained_dims` builds a set compared against `overlapping_dims`; a separate label lets a rule register two dims while only one is recorded, silently disabling the duplicate check.
  - **The bare-number parser arm requires a trailing `%` and declines on a trailing word.** The parser runs against `_segment_probe` for every rule of every carrier, and its failure mode is worse than a miss: `"NCB 25% AND ABOVE"` hitting the bare arm yields the point band `(25, 25)`, which is well-formed, in range, passes every validator, and matches almost no policy. Postfix operators are first-class arms for the same reason (cf. `_parse_range_field`, which needs the qualifier _before_ the number and silently sentinels `"6 AND ABOVE"`).

  - **`_MIRROR_DIM_KEYS` in `cpa_split.py` is the TENTH sync site, and the only one that deletes.** It enumerates a rule's coverage-independent grid slot and feeds `_mirror_signature` -> `drop_mirrored_third_party`, which removes rules outright. An NCB ladder's base tier and its marked twin are identical in every other dimension — that is what a tier ladder _is_ — so omitting the band collapses them onto one signature and lets a third-party rule mirror a comprehensive rule it does not duplicate. Measured on a real Chola document: 101 signature groups masked more than one distinct band. Adding a dimension here can only make the drop fire _less_ often, which is the conservative direction the function documents for itself. **`drop_mirrored_third_party` runs BEFORE the split inside `materialize_cpa_split` and must not be reordered** — now that third-party rules split too, a dedup running afterwards would compare a deducted `without-cpa` value against its comprehensive twin, stop recognising the mirror, and let a fabricated pair through as two rows instead of zero. Pinned by `test_cpa_split.py::MirrorDedupTests::test_dedup_still_runs_before_split_for_clause_carrying_tp`.

  Contract pinned by `cins/tests/test_ncb_tier.py`, `test_overlap_exclusion.py::NcbBandOverlapTests`, `test_cpa_split.py::MirrorSignatureNcbTests` and `commission_intake/tests/test_export_column_alignment.py`. Changing any of it means bumping `CICS_PIPELINE_VERSION`.

- **Every exported deal carries a State and an RTO, and the two are one failure** — no source grid in the corpus prices a deal without a geography. The export derives the **RTO** column from the rule's `conditions.state` whenever no explicit `conditions.rto` exists, so a state that fails to resolve blanks BOTH columns at once. That is exactly what shipped to a client on Chola 2W and commercial (GCV/PCV/Buses/MISC-D): Pass 3 had the state on every rule, but `_expand_state_names` did not know the carrier's zone tokens, so the rule's state went `None` and nothing fired — `StateColumnAlignmentValidator` is scoped to Private Car, `RowCoverageValidator` counts a state-less row as covered, and `state`/`rto` are unvalidated optionals on the schema. Four things hold this together, and all four must move together:

  - **Zone tokens live in two tables in `raw_to_cics_transformer.py`, walked by ONE loop.** `STATE_NAME_MAPPINGS` maps a token to one canonical state; `STATE_GROUP_MAPPINGS` maps a token to several (`"ne"` -> the north-east block). The loop is shared because the **boundary rule is the load-bearing part** and must not drift: a key of 3 characters or fewer is matched on `[\s,_\-\/]` boundaries, never as a bare substring — `NE` must not match the `NEW(100-500 NOP)` tier label sitting in the next cell of the same grid.
  - **A `"Rest of <state>"` token names the state, not a new geography.** `ROM` -> maharashtra, `ROTN` -> tamil-nadu and `ROK` -> karnataka are correct because their metro siblings (`Mumbai/GA/Pune/Central MH`, `TN-Chennai`, `KA (Bangalore)`) each carry an explicit `conditions.rto`, and the export's claimed-RTO complement subtracts those codes from the remainder rule's fill — the same shape as the shipped `UP` / `UP- East` pair. `ROK` travels in a **multi-state** cell (`TN/ROK` = all of Tamil Nadu plus the Karnataka remainder); before it was mapped only `tn` matched and the Karnataka half vanished from the export.
  - **The carrier's zone master is authoritative; the global RTO master is the fallback, and the ordering is the guard.** `ROM`/`ROTN`'s metro siblings are seeded in `CarrierRTOZoneMaster`, but `chola_rto_zone.csv` seeds **no bangalore zone** — so `KA (Bangalore)` claimed no RTO, the export filled it with all 71 Karnataka codes, and it collided with the differently-priced `TN/ROK` row. `_expand_rto_codes` now falls back to `match_rto_localities` (`master_data/services/resolver.py`) against a locality index parsed from `RTOMaster.value` (`KA01-Bangalore(Karnataka)(Group A)`; the trailing `(Group X)` is **optional** — `UP29`/`UP99` have none). The fallback runs **only when literal codes, `rto_mapping` master data and the carrier zone master have all missed**, so a seeded zone always wins and the fallback can only add geography where there was none. Two guards keep it from inventing geography, and both are load-bearing: candidates are **scoped to the states the same text just resolved** (48 locality names span more than one state — `Hyderabad` is both Andhra Pradesh and Telangana), and names must be **≥4 chars, word-boundary-anchored on `[a-z]`** — which is why `TN/ROK`, `KA`, `ROM`, `ROTN`, `NE`, `AP/TS` and `UP- East` all yield nothing while `KA (Bangalore)` yields exactly the 18 bangalore codes. Removing the fallback means unmapping `ROK` again. The index is built once per document in `transform()` alongside `_carrier_zone_map` — **not** via `MasterDataResolver`, which eagerly reloads every table. Guarded by `test_state_zone_tokens.py`, `test_chola_zone_expansion.py` and `master_data/tests/test_rto.py`.
  - **One zone, two spellings: `_match_carrier_zones` also matches a two-token label REVERSED.** The same Chola zone is written `UP- East` in the Private Car / CV headers and `East UP` in the Two-Wheeler key column; matching only the forward order left 115 Two-Wheeler rules with no zone, no explicit RTO, and a full Uttar Pradesh fill — silently disabling the `UP` / `UP- East` complement on that sheet. Kept narrow on purpose: **only exactly-two-token labels** are reversed (permuting 3+ tokens is combinatorial and starts matching text nobody wrote), the reversed form is still one adjacent word-boundary-anchored phrase so it can never match _more_ text than the forward form, and a reversal colliding with **another zone's forward label is dropped** rather than allowed to claim that zone's rows. Both the RTO and state paths go through this one function precisely so they cannot drift.
  - **Known limitation:** `_claimed_rto_by_bucket` is document-wide per product bucket, so a plain `KA` rule in a _different_ grid on the same document also has Bangalore's codes subtracted. Pre-existing (the `UP` / `UP- East` pair behaves the same way); scoping the claimed set per table band is a separate change.
  - **Group membership is taken verbatim from the grid, never "helpfully" completed.** Chola's north-east block excludes Manipur and Mizoram because its spelled-out sibling column does.
  - **`product_bucket` lives in `master_data/services/resolver.py` and has exactly one definition.** The commission export (which fills the RTO cell) and `StateRtoPresenceValidator` (which asserts that fill is non-empty) both call it, so they cannot disagree about what a product name means. Tokens match on **word boundaries of `[a-z]`, not `\w` and not bare substrings** — a bare substring mis-buckets "Marine Cargo" as CAR and "Business Package" as CV, and a wrong bucket is worse than none because it fills the cell with another product's RTOs; `\w` would count digits and reject ordinary grid spellings like `GCV3T` / `TW1+1`. camelCase is split (`PrivateCar`) and a plural suffix is allowed (`Buses`), because a name the boundary rejects now resolves to `None`, which both blanks the cell and raises a validator finding.

  `StateRtoPresenceValidator` is the net under all of it, and **its HIGH is fatal** (unlike `StateColumnAlignmentValidator`'s): `cics_cache.should_cache` refuses to pin a CICS output carrying any CRITICAL/HIGH, so a document with state-less rules is re-extracted rather than cached and exported blank. A missing state is HIGH; an unresolvable RTO bucket is MEDIUM (non-blocking — the product may be a non-motor line). Because a false positive walls a document out of the cache, every ambiguous case passes: unreadable master data disables the RTO half rather than failing it, and the validator deliberately does NOT model the export's claimed-RTO pre-pass (a miss is the safe direction). Rollback is `CINS_STATE_RTO_MANDATORY=false`, no redeploy, mirroring `CINS_CODEGEN_GATE` / `CINS_REGRESSION_GUARD`. Contract pinned by `cins/tests/test_state_rto_presence_validator.py`, `cins/tests/test_state_zone_tokens.py` and `commission_intake/tests/test_export_non_car_rto_fill.py`. Changing any of it means bumping `CICS_PIPELINE_VERSION` (this was 1.2.0) — otherwise a cached document keeps serving the blank columns the fix removes.

- **Make and model are canonicalized against the carrier's MMV master, and ONE matcher serves both the rewrite and the check** — a grid spells the same manufacturer `MAHINDRA AND MAHINDRA`, `Mahindra & Mahindra Ltd` and `Mahindra`, and the extractor is known to mis-land sub-class words and CC bands (`SCOOTER`, `150_350cc`) into `vehicle_make`. `CarrierVehicleMMVMaster` (`master_data/models/mmv.py`, seeded from `master_data/data/chola_mmv.csv`, ~22k Chola rows) is the reference, `master_data/services/mmv.py` is the only slugger/matcher, and both sides import it:

  - **The transformer rewrites, the validator reports, and neither owns its own matching rules.** `RawToCICSTransformer._canonicalize_make_model` folds `vehicle_make` / `vehicle_model` and their `_exclude` twins onto the master's spelling using an index built ONCE per document (`build_mmv_index("Chola")` in `transform()`, alongside `_carrier_zone_map`). The DB read is the module-level `master_data.services.resolver.carrier_vehicle_mmv(carrier)` — **never** an attribute on `MasterDataResolver`, which eagerly reloads every table it owns and would pull 22k rows for every document of every carrier. Keep new carrier-scoped, high-row-count lookups module-level for the same reason. `CholaMMVValidator` then flags whatever is still unmatched. A second canonicalization scheme on either side would flag values the other would have fixed — the same discipline `CholaProductHierarchyValidator` follows by reusing `VEHICLE_SUB_CLASS_MAPPINGS`.
  - **Ambiguity resolves to `None`, never to a guess — and "ambiguity" was measured, not imagined.** A wrong fold silently rewrites a rule to name a vehicle the grid never mentioned, which is strictly worse than leaving the source text alone and letting the validator say so. A dump of 2,237 live Chola deals (`Chola_Dump_AMJJ.xlsx`) showed the first cut of this matcher corrupting makes on **93% of them**, and four rules now hold that at zero. Each has a live counter-example; re-run the dump sweep before relaxing any of them:
    - **Exact slug only.** The unique-leading-prefix rung produced `EICHER` -> `Eicher Polaris`, `HYUNDAI` -> `HYUNDAI CONSTRUCTION CO`, `SUPREME` -> `AUTO SUPREME INDUSTRIES`. A complete, correct manufacturer name is not a prefix of a longer one just because the master happens to list only the longer one. (An earlier fuzzy/edit-distance rung was removed for the same class of reason: it matched `SCOOTER` onto `SCOOTERS INDIA`.)
    - **`_NOISE_TOKENS` is corporate-form words ONLY** (`ltd`, `pvt`, `and`, ...). Industry words are identity in the Indian CV market, not boilerplate: dropping them collapsed `OM INDUSTRIES` onto `OM MOTORS`, `STAR INDUSTRIES` onto `STAR AUTO`, `NIKHIL ENTERPRISES` onto `NIKHIL FURNITURE` — unrelated firms. The cost is that `TATA MOTORS LTD` and `TATA` no longer fold together; both are left verbatim, which is the safe direction.
    - **A slug with more than one distinct source spelling is dropped** (`_finalize`). Collect-then-reduce, never reduce-as-you-go: the old `_keep_preferred` could not tell "the same name twice" from "two companies sharing a slug" and silently kept the shorter.
    - **Canonicalization never lengthens.** With corporate forms slugged away, a master holding only `SML ISUZU LTD` would otherwise rewrite the grid's correct `SML ISUZU` into the boilerplate spelling. Dropping `PVT LTD` is a tidy-up; adding it is noise.
  - **Makes match carrier-wide; only models are product-scoped.** A make is a brand. Real Chola `Car/Taxi` deals enumerate commercial brands (`Ashok Leyland`, `Bharat Benz`, `SML ISUZU`) that the 614-row Car bucket does not hold, so product-scoping makes left half the makes in the dump unmatched for no reason but which book listed them. Models stay scoped — a short model name is only unique within its manufacturer.
  - **The sentinel `"All Other Make/Models"` is never canonicalized or flagged.** It is a bucket marker the transformer's `_clone_make_bucket` fan-out matches on as literal text.
  - **Every finding is MEDIUM, and that is deliberate, not timidity.** `cics_cache.should_cache` refuses to pin an output carrying a CRITICAL/HIGH, so a HIGH here would wall a whole Chola document out of the cache over a spelling the master merely has not got yet. This applies to BOTH halves: the spelling half (`CINS_CHOLA_MMV`) and the presence half (`CINS_MAKE_MODEL_MANDATORY`, which asserts `VehicleMake`/`VehicleModel` export non-empty). On a real Chola grid 43.5% of rules carry no make and 97.5% no model, most of it source-faithful — the Private Car grid has no MAKE/MODEL column and the CV grid prices them only on up-to-3.5T rows — so a HIGH would wall out every Chola document.
  - **Two flags, because they gate different things, and BOTH default to `false`.** `CINS_CHOLA_MMV` gates the fold AND the spelling check together (gating only the fold would leave the validator flagging spellings it would have fixed); `CINS_MAKE_MODEL_MANDATORY` gates the presence rule. Everything fails open: an unseeded/unreadable master, a missing index, an unclassifiable product or a non-Chola provider yields a clean result, not a wall of findings.
  - **The presence rule is off because the client's own data contradicts it.** The same dump carries no `VehicleModel` on **93%** of deals — 100% of Car/Taxi, 84% of CV — and no make on 8 of 2,237. Blank make/model is the shape their production system ships, and "all makes" is expressed by enumerating all 55+ of them, never by a placeholder. Do not add a placeholder/catch-all value; the client was asked and the dump answered.

  Contract pinned by `cins/tests/test_chola_mmv_canonicalization.py`, `cins/tests/test_chola_mmv_validator.py`, `master_data/tests/test_chola_mmv_masters.py` and `master_data/tests/test_chola_mmv_parsers.py`. With `CINS_CHOLA_MMV` off the transformer is a no-op, so `CICS_PIPELINE_VERSION` stays at 1.6.0 — **enabling the flag in any environment is itself a pipeline-version change** (bump to 1.7.0 and confirm `CINS_REGRESSION_GUARD`), because the `_exclude` twins are part of `_DEDUPE_SCALAR_FIELDS` and re-spelling them merges dedupe groups.

- **A CPA-deduction footnote splits every rule it touches, third-party included — and the negative case differs by column** — `cpa_split.materialize_cpa_split` bifurcates any rule with an unconstrained `conditions.cpa` that carries a `without-cpa` `conditional_deduction` clause (structured, or detected from free-text `outcome.other_conditions` via `_cpa_clause_from_notes`). The deduction comes off the rule's OWN payout column — od / net / **tp** — in percentage POINTS, not off the premium basis the clause names (the footnote is Private-Car-centric and says "OD Pay-out" even on a Net-paying CV grid).

  - **Third-party rules split and deduct like any other.** They used to be exempted on the reasoning that TP/PA is a statutory pass-through; that was wrong about what the footnote deducts — it reduces the BROKER's payout, not the statutory premium. The exemption's visible cost was that a clause-carrying TP rule stayed `cpa`-unconstrained and the exporter's `cv_default` fallback rendered ONE row whose CPA cell read the merged `"With CPA,Without CPA"` at the **undeducted** rate, overstating the without-CPA payout by the full deduction on every one of them. The incident recorded in the old test (Chola doc `dbe5b4ea`, third-party 24 -> 48 rules) is the **correct** count now: 24 TP grid cells each pricing two commercially different deals are 48 exportable deals.
  - **Two negative policies, and they must not be conflated.** od/net **clamp at 0** (`deduct_pct`, pinned by `test_deduct_pct_clamped_at_zero`) — a 1.5-point deduction on a 0.5% Two Wheeler grade would otherwise emit a negative rate that fails schema validation CRITICAL and takes the whole document down. tp **declines** (`deduct_pct_no_negative`, returns `(value, applied)`) — the row still bifurcates but both variants carry the undeducted rate, because a 0% ACT payout is a number the carrier never published and a booking system may read as "no payout at all", while the grid rate at least appears on the grid. The decline is invisible in the output (the pair just looks undeducted), so the per-document WARNING naming both counts is the only signal of how often it fires — keep it.
  - **The tp branch keys on `_is_third_party(rule) or rule_col == "tp"`, and the coverage half is load-bearing.** `rule_col` is derived from `applied_on`, NOT from `policy_type`: a third-party rule carrying no third-party `applied_on_override` falls back to `outcome.applied_on` (typically `"Net Premium"`) and would take the clamp-at-0 path on the column test alone. It is the rule's coverage, not the label on its premium basis, that makes a 0% floor the wrong answer.
  - **Only clause-carrying rules split, and that is the entire scoping mechanism.** No other carrier in the corpus writes the CPA footnote, so this is Chola-scoped in practice. There is deliberately **no carrier-name check** and **no env flag** — do not add either; a carrier that later writes the same footnote should get the same treatment automatically.
  - **`CoverageIntegrityValidator` no longer flags a CPA-split TP rule.** Its check B (a HIGH: "third-party rule(s) carry a CPA split — TP/PA-only rules are never CPA-deducted") was **removed, not downgraded**: it now describes correct output, so it would fire on every affected document, and a HIGH blocks `cics_cache.should_cache` from pinning them — making every Chola document with the footnote permanently un-cacheable. Check A (orphaned ACT columns) is untouched and can only fire less often.

  Contract pinned by `cins/tests/test_cpa_split.py`, `cins/tests/test_coverage_integrity_validator.py` and `commission_intake/tests/test_export_cpa_split.py`. Changing any of it means bumping `CICS_PIPELINE_VERSION` (this was 1.8.0) — otherwise a cached document keeps serving the single merged-label row.

- **Editing ANY file under `cins/prompts/` invalidates the whole cross-carrier CICS cache** — the cache key binds `prompt_version_hash`, a SHA256 of the entire prompt corpus (`commission_intake/cics_cache.py:8-22`), so a one-word prompt edit forces a full codegen re-roll of every cached document for every carrier, independently of `CICS_PIPELINE_VERSION`. That cache exists precisely so "a re-extraction does not re-roll the codegen dice (and cannot regress a good result into a segment-dropping one)". State the blast radius in the PR and confirm `CINS_REGRESSION_GUARD` is enabled before merging a prompt change.

- **A per-sheet key must be injective, and sheet content must never travel via a shared file** — sheets are extracted CONCURRENTLY (`pipeline.py` `_process_one_sheet` under a `ThreadPoolExecutor`) into ONE document-scoped `output_dir`, so any key two sheets share is a data-corruption channel, not just an untidy filename. Sanitize-then-truncate is not injective: four Chola June sheets shared a 60-character prefix, collapsed to one 50-char key, and the pass-content file was written and read back by four threads. Three sheets were extracted from the Two Wheeler grid and the document's whole CV book (1,552 rules across GCV/PCV/Buses/MISC-D) became 2,633 phantom TW rules — **with no exception, no validator finding at extraction time, and a plausible-looking rule count**. Only `RowCoverageValidator` caught it, after the fact. Three rules follow:

  - **Both sanitizers carry a digest of the FULL name.** `pipeline.get_safe_sheet_name` (50-char budget) and the indexer's `sanitize_sheet_key` (100-char, module-level, shared by `ContentIndexer._sanitize_sheet_key` and `IndexedDocument._sanitize_for_lookup` so they cannot drift). `_sanitize_filename` keeps the truncate-only shape because it names DOCUMENT ids, where stability beats uniqueness — do not confuse the two. `IndexedDocument._resolve_sheet_key` falls back to `legacy_sanitize_sheet_key` so documents indexed at `INDEXER_VERSION` <= 1.8 still load. Changing either sanitizer means bumping `INDEXER_VERSION` (this was 1.9) so already-indexed documents re-key.
  - **Pass content is passed in memory, never round-tripped through disk.** `build_pass_contents` returns the three strings; use them. The `pass{1,2,3}_content_*.txt` writes are debug artifacts with no reader. `prepare_extraction_request` is a bare file read with no transform, so the hop only ever added risk.
  - **`_table_shape_for_sheet`'s `original_sheet_name` fallback is load-bearing, not a nicety.** The pipeline and indexer sanitizers deliberately do not agree, so the direct key hit is best-effort and the fallback is the real lookup.

- **An empty Pass-3 result is only a failure when the sheet HAS rate rows, and proving "no rate rows" takes THREE witnesses** — a notes/conditions sheet (payout-terms prose, zero rate cells) correctly yields nothing. Treating that as a failure costs three LLM retries and then sets `overall_requires_review`, which makes `cics_cache.should_cache` return False **permanently** for that document: every later access re-runs full codegen with no backoff, and it can never pin. Chola's May'26 `conditions` sheet sat in exactly that state across repeated re-extractions. But suppressing a failure signal is far more dangerous than raising one — a clean empty gets PINNED TO CACHE — so the branch fires only when every one of these agrees, because each alone has a blind spot that admits a genuinely dropped grid:

  - **`declares_only_non_rate_tables` (structural, load-bearing).** Every `[type: ...]` marker in the content is `notes`/`master`. The markers come from the indexer's table tagging, so they survive whatever the rate cells look like. Fails SAFE: content with no markers at all, or any marker outside notes/master, reads as rate-bearing.
  - **`count_rate_bearing_rows_markdown` (heuristic).** `_is_rate` is a strict `fullmatch(r"-?\d+(\.\d+)?%?")`, so a real payout grid whose cells read `22.5 %`, `Upto 25%`, `25%-30%` or `Rs 500` counts **ZERO**. This can never be the only witness — that is exactly how a dropped grid would ship as clean.
  - **`expected_rate_cells(table_shape) == 0` (index-time CSV count).** An independent view that survives a mangled markdown conversion. Returns 0 for an absent/legacy shape too, so it adds evidence but never proves emptiness alone.
  - **`not best_entries`.** A gate-forced retry can land here after an earlier attempt really did extract rows; returning empty would discard them, the gate manufacturing the drop it exists to prevent.

- **GCV has no body dimension, and the strip must run LAST** — a goods-carrying grid prices by WEIGHT BAND. Four things hold it together:

  - **The strip is absolute and carrier-agnostic.** A body genuinely resolved from a slug (the `auto-rickshaw` / `e-rickshaw` off `1_GCCV_3W`) goes too, and the gate is `product_subproduct == "commercial-gcv"` with **no carrier check** — a goods-carrying grid prices by weight whoever published it. Rollback is `CINS_GCV_NO_SUBCLASS=false`, no redeploy; flipping it is itself a pipeline-version-relevant change.
  - **Ordering: last in `_transform_product`, after `_bifurcate_gcv_wheels`.** Three writers run after `_transform_conditions` returns, so a strip inside the conditions chain is simply undone: the product-level backfill re-adds an `inferred_sub_class` from the source section, `_bifurcate_subclass_buckets` clones body enumerations, and — the dangerous one — `_is_four_wheel_only_subclass` is the SOLE 4W-only signal for the special-purpose bodies that carry no GVW band (tractor, excavator, harvester, bus, maxicab). Strip before bifurcation and every one of them falls through to the both-wheels arm and grows a spurious 3W clone: the `(0,0)` catch-all regression that logic exists to kill. Run after it and the scoping survives in `number_of_wheels`.
  - **The strip must be followed by a second `_collapse_duplicate_rules`.** Subclass-only clones become byte-identical once the field is null, and `rule_overlap_checker._constraint_state` returns `_NEITHER` for a dimension null on both sides — so `_conditions_identical` holds and each pair is a **CRITICAL** `complete_overlap`. The collapse merges only when the OUTCOME matches too, so **differently-priced bodies deliberately survive as a genuine conflict**: the only dimension that told them apart is gone, and silently merging them would pick one rate arbitrarily. Do not "fix" that CRITICAL by widening the collapse.
  - **The body word survives as `rule_id` provenance, and TWO HIGH validators depend on the carve-outs.** `CholaProductHierarchyValidator`'s mandatory-presence check is exempted for `commercial-gcv` (gated on `product_subproduct`, not the free-text `sub_category`) — it would otherwise fire on every GCV rule, and a HIGH blocks `cics_cache.should_cache`, walling the carrier's whole CV book out of the cache. `RowCoverageValidator`'s declined-row check (the empty-rate `4_OTHERS` row, also HIGH) was satisfied by the very `not-available` sentinel being deleted, so `_strip_gcv_subclass` appends `_SC_<body>` to the `rule_id`, which is already in `_coverage_blob` and excluded from `_duplicate_collapse_key`. The validator was **not** weakened. (`1_GCCV_3W`'s `gccv` body token flagging is pre-existing and unrelated — it fires on the old values too.)

- **A commercial-vehicle renewal rate prices rollover too** — a rollover IS a renewal that changes carrier, and no CV grid in the corpus prices the two apart: the carrier publishes one renewal rate card and books both against it. Exporting the bare `renewal` left a rollover quote matching no deal at all. `_imply_rollover_on_renewal` appends `rollover` to any CV rule whose `business_type` already contains `renewal` (`CINS_RENEWAL_IMPLIES_ROLLOVER`, default ON).   - **Scoped to `CV_SUBPRODUCTS`, and carrier-agnostic.** It is a fact about how commercial rate cards are written, not about Chola — a carrier that later publishes the same shape gets it automatically. Private Car and Two Wheeler are excluded because their grids DO sometimes price rollover separately, and widening there would fabricate an overlap on a dimension the grid uses.
  - **An absent `business_type` stays absent.** `None`/`[]` exports a BLANK BusinessType cell; filling it would be a different claim ("this deal covers every business type") than the one this rule makes.
  - **It runs BEFORE `_collapse_duplicate_rules`**, so a grid that spells one row `renewal` and another `renewal,rollover` at the same rate dedupes to one deal, while the same pair at different rates survives as a genuine conflict for the overlap checker to report. Moving it after the collapse ships the duplicate.
  - **`rollover` is APPENDED, not sorted in.** The export comma-joins the list verbatim, so list order is the cell text the client reads.

- **A Chola PCV body class is read off the segment label, and the seating band is supplied — never the reverse** — the client's spec is the sole authority here: `0-5` seats is a Normal Taxi (bifurcated further by CC), `6-12` a Maxi Cab, `13-16` a Big Taxi. No Chola grid states a seat count; the `PCCV < 6` / `PCCV > 6` tables write only `UPTO 5` / `ABOVE 6`, and `ABOVE 6` parses to the open `(6, 99)`, which spans BOTH upper bands. So `_apply_chola_pcv_subclass` takes the body from the segment label (`3_BIG_TAXIS` → `taxi` → promoted to `greater-than-six-seater`, `4_MAXI_CAB` → `maxicab`) and `_PCV_MAXI_CAB_SEATING` / `_PCV_BIG_TAXI_SEATING` supply the real range. Inverting that direction — deriving the body from seats — cannot work on this corpus. Four things to know:

  - **The constants shipped INVERTED, and the failure mode is invisible in the obvious column.** `_PCV_MAXI_CAB_SEATING` held `(13, 16)` and `_PCV_BIG_TAXI_SEATING` held `(6, 12)`. `VehicleSubClass` was correct throughout — only `SeatingCapacityStartRange`/`EndRange` were swapped between the two bodies, so every review that checked body classes passed. Whatever else changes here, assert the band and the body **together**; `test_chola_pcv_subclass.py::test_maxi_cab_and_big_taxi_bands_do_not_overlap` exists for exactly that.
  - **The 13-16 band emits `big-taxi`, NOT `greater-than-six-seater` — the carrier master cannot express this split at all.** Chola's `CV/PCV` hierarchy lists exactly three bodies: `Taxi`, `Greater Than Six Seater`, `Kaali Peeli Taxi`. There is no Big Taxi row and no Maxi Cab row. And `Greater Than Six Seater` is a single >6 bucket, not the 13-16 band — the carrier's own MMV book files BOTH `ALFBV 6/16, 12 SEATER` and `ALFBV 6/16, 16 SEATER` under it, so it spans the client's Maxi Cab band too and reads as the 6-12 name if anything. Emitting it for 13-16 merged two commercially distinct deals under one label. `big-taxi` was added to the enum for this; `maxicab` was already in the same position. Both raise a MEDIUM from `CholaProductHierarchyValidator`'s membership check — which is **MEDIUM by design and does NOT block the cache pin**, unlike its mandatory-presence HIGH. The real fix is the carrier adding both rows to their hierarchy master; until then the MEDIUMs are expected, not a regression.
  - **`big taxi` / `big taxis` must NOT fold onto plain `taxi` in `VEHICLE_SUB_CLASS_MAPPINGS`.** They used to, and `taxi` is the exact slug `pcv_taxi_mirror` clones into Private Car — so the alias quietly fed 13-16 seat commercial vehicles into a Private Car product. The mapping now yields `big-taxi`, and `_apply_chola_pcv_subclass` accepts BOTH spellings (`big-taxi` present, or `taxi` with `seat_start >= 6`) so a grid that writes the body out directly still picks up the band instead of keeping the raw `(6, 99)`.
  - **There is deliberately no 17+ bus band in this function.** Buses route to the separate `commercial-buses` sub-product as `school-bus` / `staff-bus` via the overlay; the enum has no bare `bus`, and emitting one from a PCV-scoped function would name a body the PCV hierarchy master does not carry and trip `CholaProductHierarchyValidator` — a HIGH, which blocks the cache pin.
  - **The two body-keyed arms must run BEFORE the `4w-and-above` gate, or they are dead code.** The overlay sets `number_of_wheels` only on the `PCCV < 6` table; every `PCCV > 6` row — which is to say every Big Taxi and Maxi Cab there is — carries none. With the arms behind the gate, live output (doc `5f29236b`) showed 24 maxicab and 18 taxi rules all still on the raw `(6, 99)` sentinel, and the bands had never once applied in production. The arms only REFINE a body the source already named, and `maxicab` is in `_FOUR_WHEEL_ONLY_SUBCLASS_STEMS` anyway, so a wheel check protects nothing there. The `<=5 → taxi` arm is different — it INVENTS a body the source did not name — and stays behind the gate.
  - **`pcv_taxi_mirror` reads the exact `{"taxi"}` slug set, so only the 0-5 band mirrors — which makes a failure of the Big Taxi arm leak into Private Car.** While that arm was dead the Big Taxis kept the bare `taxi` slug and all 18 were cloned into a `Private Car / Taxi` product: a 13-16 seat commercial vehicle exported as a private car deal. The mirror is therefore a _downstream check_ on this function, not an independent feature — when the arms change, re-count the `_PCTAXI` product, don't just diff the seating columns.

No env flag — this is a deterministic client-specified mapping, not a rollback-able behaviour change. Fixing the inversion moved `CICS_PIPELINE_VERSION` to 1.11.0; rule counts are unchanged, so `CINS_REGRESSION_GUARD` does not fire on the re-extraction.

- **An all-zero grid row is a DECLINED segment, not an empty one — and `RowCoverageValidator` currently cannot see when one is dropped** — Chola's `PCCV > 6` table has five rows, not four: `1_SCHOOL_BUS`, `2_STAFF_BUS`, `3_BIG_TAXIS`, `4_MAXI_CAB` and `5_BUS`. The MSV table likewise ends in `4_OTHERS`. Both trailing rows carry exactly four non-blank cells, all `0` — the carrier explicitly declining that segment, which the booking system still needs a zero-payout rule to match against. On doc `5f29236b` Pass-3 codegen emitted **zero** rules for either one (`5_BUS`: 0 occurrences in the pass-3 result, against 18 for `3_BIG_TAXIS` and 88 for `1_SCHOOL_BUS`), so Buses and MISC-D each silently lost a documented segment. `5_BUS` was never named in the overlay at all; `4_OTHERS` was, with an explicit "Do NOT skip this row", and was dropped anyway — so **the prose instruction alone is not sufficient**, and any change here needs verifying against a real re-extraction rather than assumed from the prompt text.

  - **The net that should have caught this is blind, and both blind spots are the same defect.** `RowCoverageValidator._body_covered` probes a bare substring against a DOCUMENT-WIDE blob that includes product names, rule ids and rule text. `5_BUS` normalizes to the body token `bus`, which is masked by `buses` (the `Buses` sub-category) and by `school bus` — so a generic bus row is _structurally_ always "covered" on any document that has a Buses product. `4_OTHERS` takes the `_DECLINED_BODY_TOKENS` branch, whose `"others" not in blob` test is masked by **Two Wheeler** rules carrying a `vehicle_sub_class` of `others`: the check is not segment-scoped, so a TW body masks a MISC-D drop. Measured: 0 row-coverage findings on a document that dropped two declined rows. **Not yet fixed** — the sound repair is to key the declined-row test on the row's own slug (the blob does contain `1_school_bus`, `4_maxi_cab` for rows that survived) and to scope it to the sheet's own segment, but a false positive here is a HIGH, and a HIGH blocks `cics_cache.should_cache` and walls the document out of the cache entirely, so it needs its own change with real-document evidence.
  - **Do not classify a declined row by its label.** `5_BUS` is all-zero on the Apr-26 and Aug-25 grids but could carry real rates on a later one; `_is_rate` matches `0`, so such a row reads as rate-bearing. The property that makes it declined is that every rate cell is zero, not what it is called.

- **MISC-D bodies share one rule, and the merge is per SOURCE rule** — the client prices Agricultural Tractor and Harvester as their own deals and treats every other MISC-D body as one bucket, so the per-body fan-out turned a single "Loader, Excavators/Earth Movers, Crane, Bulldozers, Road Rollers, Fork Lift Trucks" grid cell into six deals at one rate: six rows to reconcile where the carrier books one. `_bifurcate_subclass_buckets` now emits one rule per `_MISCD_KEEP_OWN_RULE` body plus ONE multi-value rule for the rest (`CINS_MISCD_SUBCLASS_MERGE`, default ON). Five load-bearing decisions:

  - **It lives in the fan-out, not in a CICS post-processor.** The requirement is "do not fan THIS rule out"; after the fan-out the only handle on "same source rule" is the `_SC_` suffix, and `cpa_split` emits both its variants under one `rule_id`. Suppressing the fan-out is exact by construction and makes "never merge two distinct source rules" true without a check — each source rule yields exactly one merged rule, at its own rate. A post-processor would also have to re-derive `_collapse_duplicate_rules`, `_dedupe_range_overlaps`, `_normalize_boundary_overlaps` and `_strip_gcv_subclass`, all of which run after it.
  - **The merged list comes from `CarrierProductHierarchyMaster`, not from the document** — the carrier's deal records enumerate the whole class, the same reasoning the export's `sub_class_cell` widening rests on. But the widening is guarded: it replaces every rest-bucket rule's bodies with the SAME list, so body type stops telling those rules apart. Fine while another dimension still does (every MISC-D grid has an ACT rule and a PACK rule, differing on coverage). NOT fine when two rest buckets are identical in every dimension BUT body at different rates (`{crane, loader}` at 10% vs `{excavator}` at 12%) — widening those makes them overlap on every body and price one vehicle twice, a HIGH from `rule_overlap_checker` that blocks the cache pin. So `_subclass_free_signature` keys the guard, **not a bare rule count**: a count-based guard would see the ubiquitous ACT/PACK pair and never widen anything. Two further narrowings, each of which the guard needs or it disables itself: a collision requires **different bodies** (two rules with the same signature AND the same body already conflict today — widening does not create that, and counting it would let one pre-existing duplicate switch the merge off for the whole product) and **different rates** (same slot, same rate, different bodies is exactly what the merge exists to fold into one deal; those rules collapse together immediately after).
  - **A MISC-D singleton IS widened, and assuming otherwise made the whole feature a no-op.** The first cut skipped `len(vehicle_sub_class) <= 1` on the reasoning that a rule which resolved one body is not a fan-out candidate. But the real Chola MSV table does not enumerate its bodies in one cell — it publishes ONE ROW PER BODY (`1_TRAC`, `2_EXCAVATOR`, `3_HARVESTOR`), so every MISC-D rule reaches the merge already a singleton and nothing was ever merged. Outside MISC-D the singleton short-circuit stays. A lone Agricultural Tractor / Harvester row still passes through untouched, keeping its original `rule_id` — it is already the shape the client asked for.
  - **A master value that fails to normalize is invisible, and it breaks TWO things at once.** The hierarchy master is stored carrier-verbatim, misspellings included — Chola's own workbook says `Excavaters`, `Buldozer`, `Tranist Mixer`, `Refridgerated Van`. `canonical_subclass_slugs` silently drops anything `VEHICLE_SUB_CLASS_MAPPINGS` cannot fold, so those rows were simultaneously (a) narrowing the MISC-D merge's widened body list — 22 bodies where the carrier books 25 — and (b) making `CholaProductHierarchyValidator` reject `excavators` and `bulldozer` as "not valid for CV/MISC-D", slugs the grid legitimately produced from its `Earth Movers` / `Bullgraders` cells. The two symptoms look unrelated and have one cause. **Fix it with an alias in `VEHICLE_SUB_CLASS_MAPPINGS`, never by correcting the CSV** — the master is deliberately verbatim, and a grid spelling the same typo has to fold too. `carrier_subclasses.py`'s docstring used to argue these typos were self-consistently fine; that reasoning was wrong, because the rule side reaches the correct slug via an alias while the master side had none. Pinned by `master_data/tests/test_chola_masters.py::test_every_master_body_normalizes_to_a_slug`, which fails on any future master value with no slug.
  - **`canonical_subclass_slugs` (`processors/core/carrier_subclasses.py`) is the ONE crossing between the master's spelling and the rules' slug space**, shared with `CholaProductHierarchyValidator` — a second normalization scheme would let the transformer widen to a spelling the validator then flags. `drop_sentinels` is the only difference between the callers: the validator accepts `not-available` (recording the absence of a body is valid), the transformer must not (the sentinel names no vehicle). The module is deliberately NOT memoized — the seed changes between tests and carrier uploads, and a module-level cache would serve one test's master to the next; callers memoize per instance instead.
  - **The DB read is lazy and fails open.** `RawToCICSTransformer` is constructed as a pure object by `CholaProductHierarchyValidator` itself and by unit tests that want only `_normalize_list_field`, so `_canonical_subclass_slugs` reads on first use and caches on the instance — never in `__init__`. An unseeded, unreadable or unmigrated master yields `[]`, and the merge falls back to the rule's own bodies. It never emits an empty `vehicle_sub_class`.

- **The stale-GCCV leak guard matches the token ANYWHERE in the row, not as a prefix** — Chola's four CV tables reuse one copy-pasted header template, so the GCCV table's trailing `1_GCCV_3W` merged-header value also sits in the PCCV<6 / PCCV>6 / MSV headers, and when Pass-3 codegen emits those as real rows they segment into PCV / Buses / MISC-D while still naming a goods carrier. `_names_gccv` is the drop test, and it was originally `rule_text.startswith("gccv")`. The real May'26 leak spells the row `GCV 1_GCCV_3W AP ACT` — the SHORTER `GCV` opens it, the GCCV token lives in the segment slug — so the prefix test dropped **none** of the 222 phantom rows, and 148 of them exported as MISC-D `auto-rickshaw`: a three-wheeled goods carrier filed as a miscellaneous-D deal, a vehicle the carrier does not sell under that sub-product. Three things keep the widened test from over-firing: it is word-boundary anchored (`(?<![a-z0-9])gccv(?![a-z0-9])`), it deliberately does NOT match the shorter `GCV` (which opens most legitimate commercial rows of every segment), and it reads BOTH the rule text and the raw `vehicle_sub_class` slug — the slug is where the token actually lives, and reading only one field is how the original test came to miss the whole class. Every dropped row is named in a warning so a false positive stays auditable. Carrier-gated to Chola and segment-gated to PCV / Buses / MISC-D: a GCCV label in a passenger or misc segment is unambiguously a leak, while the legitimate GCV copy is untouched.

## When changing Pass 0C

Before touching `pass0c_table_detection_prompt.md`, `content_cleaning.detect_csv_tables`, or `indexer.py`'s table-split block, read the rationale at the top of `_dedupe_overlapping_table_ranges` **and `_split_side_by_side_tables`**. Any change that

- alters the meaning of `start_row` / `end_row` in the response schema,
- removes the column-band guard (`start_col` / `end_col`),
- drops the `table_type` filter,
- loosens the side-by-side split's key-signature or separation guard,

must come with a new fixture in `test_table_dedupe.py` and a documented rationale here. The dedupe pass is load-bearing: a regression silently inflates rule counts by 5-10x without surfacing any validation error.
